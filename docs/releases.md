# Tack release procedure

Tack releases use tags such as `tack-v0.1.1` (stable) or `tack-v0.1.0-rc.1` (candidate). Chisel's inherited `v*` release and Docker promotion jobs are restricted to `jpillora/chisel`; they cannot publish from this repository. Tack publication writes only to this repository's GitHub Releases.

1. Commit reviewed changes in separate logical batches and push `master`.
2. Check both the `CI` and `Tack` workflows for the candidate commit, including `Spelling`; do not inspect only the Tack workflow. Wait for the native Linux, Windows and macOS tests, race checks, legacy tests, Node cross-builds and native protected-build jobs. Review local resource/fault evidence in [the validation record](../management/VALIDATION.md).
3. Write `.github/releases/tack-VERSION.md`, including compatibility limits, state migration and backup requirements. Tag the tested commit `tack-vVERSION` and push that tag.
4. The Tack tag workflow repeats native/legacy tests, both HTTP resource tests, fixture benchmarks and protected-build jobs, then builds archives. It also runs resource and intermittent-link gates and the unified shell/tunnel/reconnect smoke test on the exact packed Linux Node extracted from the final archives. It verifies gzip/ZIP integrity and the exact archived bytes, checks native version output, executable headers and hash-bound build records, and creates `manifest.json` and `SHA256SUMS`.
5. Only after all checks pass does the workflow create a **draft** release. Download the draft's actual assets, verify their SHA-256 checksums and manifest commit against the tag, and inspect the asset matrix. Publish the verified draft using `gh release edit TAG --draft=false`; keep candidate releases marked prerelease. For a stable release, use `--prerelease=false --latest` when publishing the verified draft. Publishing does not promote Docker tags or rebuild assets.

Install pinned protection tools with `python3 -B scripts/install-build-tools.py --output bin/build-tools`, then use `python3 -B scripts/build-release.py --version VERSION --output EMPTY_DIRECTORY` to reproduce packaging locally. The default profile is `packed`; `--protection obfuscated` and `--protection plain` produce comparison builds. Publication uses `--require-clean`. Verify downloaded v2 archives with `python3 -B scripts/verify-release.py DIRECTORY --commit EXPECTED_COMMIT`. The verifier executes native version commands after validating checksums; use it only with trusted release artifacts. `--native-only` is a packaging smoke test and cannot replace the release matrix. The build script never overwrites existing output files. Publication must use the clean, tagged CI checkout; local smoke artifacts may contain uncommitted development changes and must not be uploaded as release artifacts.

| Component | Toolchain | Artifact targets |
| --- | --- | --- |
| Modern `tack-node` | Go 1.26.3, CGO disabled | Linux amd64, 386, ARM v5/v6/v7, arm64, MIPS/MIPSel/MIPS64/MIPS64el soft-float; Windows amd64, 386, arm64 |
| Legacy `tack-node` | Go 1.23.12, CGO disabled | The same 10 Linux targets; no Legacy Windows artifacts |
| `tack-control` | Go 1.26.3, CGO disabled | Linux amd64/arm64; Windows amd64 |
| `tack` operator CLI | Go 1.26.3, CGO disabled | Linux and macOS amd64/arm64; Windows amd64/386/arm64 |
| `chisel` tunnel | Go 1.26.3, CGO disabled | Same architecture matrix as `tack-node`, using the modern runtime |

There are 46 archives, plus the manifest and checksums. Every new v2 archive contains its executable, license, operation guide and `BUILD.json`. The public manifest repeats the build record and includes each archive hash. Linux/macOS use `.tar.gz`; Windows uses `.zip`. MIPS filenames explicitly state `softfloat`, and ARM filenames state the ARM version. Modern filenames remain unchanged; the additional Linux Legacy Node filenames end in `_legacy.tar.gz`. Both variants embed Chisel and use the same Node entrypoint/configuration/state format. Select one client per customer device using the [compatibility guide](legacy-compatibility.md). Legacy keeps obfuscation without packing because the tested UPX loader fails on the qualified old kernel; this exception is explicit in its build record. BusyBox is supplied separately. rc.1–rc.3 were ordinary unsigned builds. New builds use the pipeline described in [build protection](build-protection.md); this does not imply signing or completion of the commercial-release stages.

The default `--node-runtime both` is mandatory with `--require-clean`. For both native protection checks and final tag archives, `scripts/qualify-legacy.py` verifies the exact Legacy binary on the pinned CentOS 6 kernel, checks both directions of state replacement, and runs both HTTP versions of the resource and intermittent-link gates. These checks precede draft creation; preserve their JSON/logs as workflow artifacts. `--node-runtime legacy` on the verifier selects the Legacy binary for extraction, while `--require-packed-node` remains a Modern gate.

The resource workflow is also runnable through `workflow_dispatch`. Its short tests and the longer local tests exercise faults and lifecycle cleanup, not 24–72 hour device endurance. The old-kernel fixture uses a real CentOS kernel with minimal BusyBox userspace, not a complete vendor installation. Native Windows amd64 CI does not validate every Windows architecture. NAS storage, overlay, ARM/MIPS hardware, other old kernels and power-loss tests must be recorded separately before promoting those combinations to supported deployment targets.
