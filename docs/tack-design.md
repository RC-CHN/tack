# Tack 集中管理设计

项目名称统一为 Tack：控制端为 `tack-control`，客户侧节点为 `tack-node`，管理 CLI 为 `tack`，部署 skill 为 `tack-deploy`。本文中的 Node 指客户侧运行程序。Chisel 专指底层隧道组件，保留其上游来源、模块名与许可声明。

本文定义托管控制平面、客户侧 Node、跨平台任务执行和发布保护的实现边界。控制平面由产品提供方托管；Node 与控制端独立部署、独立构建和发布，通过版本化协议通信。基础操作是指定一个稳定节点身份执行一个非交互任务，批量操作在此基础上展开。

## 已确定的需求

| 范围 | 决定 |
| --- | --- |
| 部署 | Controller 自行托管，Node 安装到客户设备 |
| 精细控制 | 每个任务绑定 node_id，指定程序或脚本、解释器、目录、环境变量、超时和输出上限 |
| 终端 | 不实现交互终端、PTY、ConPTY |
| 操作入口 | API 与 CLI，不要求 Web 界面 |
| 部署路径 | 部署 skill 根据目标机器生成路径与常驻方案；Node 不负责部署、安装、自启或路径选择 |
| 主平台 | Linux 和 Windows |
| 旧系统 | CentOS 6 为明确兼容目标，必须在真实旧内核虚拟机验证 |
| 嵌入式 | ARM、ARM64、MIPS、MIPSLE 等尽力支持，区分编译、模拟器和真机验证等级 |
| Shell | 支持直接执行、POSIX sh、BusyBox、Bash、Zsh、PowerShell、CMD |
| 回退 | 只有声明兼容 POSIX 的任务才允许回退 BusyBox；任务启动后不得更换解释器重跑 |
| 保护 | Node 默认混淆并尝试加壳，逐平台验证后交付；不兼容目标记录发布例外 |
| 授权 | 客户、节点额度、功能和有效期由托管控制端检查 |

## 架构与代码边界

```text
管理员 CLI / API
          │ 管理 API
          ▼
Controller ── 节点身份 / 权限 / 任务 / 审计 / 存储
          ▲
          │ Node 主动建立的 HTTPS 管理连接
          │ 注册、心跳、领取任务、取消、结果补传
          │
Node 单进程 ─── 本地任务日志 / 执行器 / 可选外部 BusyBox
          │
          └── 内嵌 Chisel 客户端库 ── 隧道连接 ── Chisel 服务端
```

管理连接独立于 Chisel 数据连接。隧道重新配置或断开不会主动终止管理连接。当前 v2 使用 HTTPS 长轮询和独立输出上传连接，保持标准库实现和 Legacy 工具链兼容。v1 周期轮询保留用于逐步升级。

`management/protocol` 定义协议；`management/control` 提供控制端；`management/node` 保留只依赖 Go 1.23 标准库的管理执行器。正式客户侧入口为根模块 `cmd/tack-node`，通过 `internal/nodeapp` 将管理执行器与 Chisel 客户端编进同一个程序，不启动外部 Chisel 客户端。Modern 使用 Go 1.26.3，Linux Legacy 使用 Go 1.23.12 与固定依赖适配器，均提供完整双功能。Legacy amd64 已通过 CentOS 6 的 2.6.32 内核虚拟机验证；对应 UPX 产物启动失败，因此 Legacy 保留整体混淆但跳过加壳。详见[兼容构建、选包与回退](legacy-compatibility.md)。管理专用构建不能冒充统一客户端。

Tack 模块使用本地命名空间 `tack.local/management/...`，通过相对路径 replace 在仓库内构建，不依赖另一个远程仓库。新版本继续读取已有 JSON 配置和旧 journal，保留 v1 协议端点和 agent.lock。v2 会新增状态字段，旧二进制不支持直接读取所有新状态；升级前备份，回退时保留执行证据并按运行说明核对任务记录。

客户侧交付一个 `tack-node` 二进制、一份配置、一个前台进程；`tunnel` 配置驱动内嵌客户端。外部部署层只负责安装路径、运行账户、挂载顺序、服务启动和卸载。管理状态恢复并获得独占锁后启动隧道，控制端暂时不可达也不阻止隧道连接。两条连接独立重连，正常退出统一释放监听器、连接和任务资源；本地不可恢复错误退出整个进程交由外部服务管理器处理。配置当前在启动时加载，集中更新隧道规则与热更新尚未实现。详见[一体化客户端](unified-node.md)。

## 身份和通信

node_id 由控制端分配，不能使用 IP 或可变主机名充当身份。显示名称、OS、架构、主机名和解释器能力是节点上报的信息，不授予额外权限。

第一阶段使用预配置节点：每个节点有独立随机凭据，管理员凭据与节点凭据分离。节点只能同步自己的状态、接收自己的任务并报告自己的结果。节点凭据不能调用管理 API。Node 接入监听器不挂载管理路由；管理 API 单独绑定回环地址，通过控制服务器本地 CLI 或管理员 SSH 转发操作。后续引入短期注册令牌、节点证书轮换、客户隔离、操作员 RBAC 和在线撤销机制。

Node 默认只连接 HTTPS，验证服务端证书，可配置私有 CA。拒绝携带凭据的跨地址重定向。开发用明文 HTTP 必须显式启用且限制为字面量回环地址。生产网络不允许跳过证书校验。

可选的 [有界整形与 TLS 指纹](traffic-obfuscation.md) 已接入管理 HTTPS 和 Chisel WSS：`bounded-v1` 在 TLS 内双向处理前 8 帧，每方向发送前缀、帧头及填充总预算 256 B（接收端保留 v1 的 1 KiB 上限），空闲不填充。Legacy Node 可用 native 整形；现代构建可用固定 Chrome 133 模板或 `personalized-v1` 客户端专属模板。后者首次生成身份种子并保存，后续重连/重启复用同一结构，TLS 密码学随机源不受种子影响。服务端先启用、同端口兼容普通 HTTP/1.1；客户端要求整形时无静默降级。证书、Node token 和 SSH 认证保持原机制，尚无真实跨境抗识别结论。

所有任务和结果使用带版本的 JSON 协议，限制请求体大小，拒绝未知字段和不支持的协议版本。stdout 和 stderr 作为字节传输，JSON 使用 base64，避免假定 Windows 输出一定是 UTF-8。可读文本转换属于展示层。

### 客户节点失陷边界

按照节点凭据可能被提取或被原机滥用设计。普通低权限入侵可通过独立运行账户、配置文件权限和 Windows ACL 限制读取；Node 同等权限或 root 入侵不能依赖本地加密、加壳或混淆保证秘密不被访问。第一阶段的随机节点 token 是开发基线，不宣称实现凭据不可导出。

生产身份方案为节点本地生成独立私钥、一次性注册令牌换取短期节点证书、按节点撤销和轮换。带 TPM 或其他硬件密钥设施的设备可以使用不可导出私钥；无硬件设备采用软件密钥并明确标记保护等级。即使私钥不可导出，被控制的设备仍可能调用其签名能力，服务端权限边界不可省略。

节点身份仅用于该节点的管理接入，不能用于管理员 API、SSH 登录、数据库、授权签发、更新发布、其他客户或通用 Chisel 中继账号。注册令牌不得长期保留在客户端。管理接入不提供任意 URL 请求或文件读取代理；后续 Chisel 中继独立部署和授权，对到控制基础设施及其他客户网络的流量默认拒绝，再开放明确需要的目标。

托管部署区分客户可达接入服务、管理入口和存储网络。第一阶段为不同监听器；生产阶段还需按实际部署实现进程或容器隔离、网络出口限制和节点请求配额。恶意节点可伪造自己的运行状态和输出，控制端不得把节点自报内容作为提升权限或更换身份的依据。

## 任务执行语义

任务包含 task_id、node_id、执行模式、程序与参数或脚本、工作目录、环境变量、超时秒数、输出上限、创建时间。批量任务创建时固定节点清单，每个节点获得独立任务和结果。

| 模式 | 行为 |
| --- | --- |
| exec | 直接启动程序并传参数，不经过 shell |
| posix-sh | 使用探测成功的系统 sh；缺失时允许配置的 BusyBox ash 回退 |
| portable-sh | 固定使用指定 BusyBox ash 和该构建携带的 applet |
| bash / zsh | 指定解释器缺失时报告不支持，不回退 |
| powershell | 显式选择可用 PowerShell，使用非交互文件模式 |
| cmd | 使用 Windows CMD 文件模式 |

解释器按固定规则在执行前解析，实际路径记录在结果中。脚本写入任务私有目录，由选定解释器直接读取，避免把用户输入再拼成一层 shell 命令。stdin 默认 EOF。工作目录和环境变量由执行器设置。所有任务默认以 Node 服务账户运行，第一阶段不实现切换用户或自动提权。

状态流转为 queued → dispatched → running → succeeded / failed / timed_out / canceled。进程无法启动与非零退出均明确记录错误及退出码是否有效。节点中断恢复后不能确认已启动任务的结果时，记录 unknown，不自动重跑。

控制端先持久化任务及派发状态再返回；Node 先持久化 task_id 和启动意图再启动进程。同一 task_id 重复下发时读取本地记录，禁止重新执行。任务执行与单次网络连接解耦，断线时继续到本地超时；结果保留本地并重试回传。此协议不承诺任意外部副作用的 exactly once。手动重试必须创建新的任务。

每个 Node 同时执行一个任务，超限输出仍持续排空管道并标记截断。v2 先在控制连接提交终态元数据、长度和输出摘要，另用独立 HTTP 连接池上传 stdout/stderr，每块最多 64 KiB，按控制端确认的持久化偏移续传。元数据确认后标记 result_pending；最终完整性校验和状态落盘完成后才确认完整结果。v3 会话采用 Node 存储格式 v4：每份非空输出独立写入 state_dir/results，小 journal 只保存元数据；上传复用一个分块缓冲区。Node 将完整结果确认持久化后才删除本地输出，再交换并回收回执。丢失确认、重复分块和重启均不重新执行命令。确认后的历史按容量和期限回收；执行过程中的实时输出流仍未实现。

Node 和 Controller 默认关闭常规诊断日志；排障时显式选择 -log-stderr 或带容量限制的 -log-file，致命错误仍写 stderr 并返回失败。任务结果、确认记录和重放水位不属于可关闭的诊断日志。升级备份必须保留整个 Node 状态目录，包括 results 和恢复文件；旧 Node 不支持 v4 存储，不能只替换二进制降级。

控制端等待中的长轮询在新任务或取消提交后立即唤醒；任务结束时 Node 主动更新等待请求。应用层空闲心跳默认 1800 秒，每次随机 ±50%，可通过 heartbeat_seconds 显式配置。租约默认 max(90, 5 × heartbeat_seconds)，即默认 9000 秒，lease_seconds 可独立调长；租约表示允许状态陈旧的时间，不代表当前连接一定可用。实例标识保存在节点状态目录，普通进程重启可以立即续接，另一实例复用同一节点 ID 则受租约限制。断线独立触发指数退避重连，不等待下一次心跳。离线节点只能在连接恢复后接收取消，本地超时始终有效。

长轮询使正常连接下的下发不受心跳间隔限制；反向代理/负载均衡的读超时和最大请求时长必须覆盖最大等待值（默认部署建议至少 2800 秒）。TCP 保活与应用层心跳分开，NAT 静默丢弃连接仍会影响实际送达时间。不能将本地 HTTPS 测试时延当作跨境网络的保证。

Node 使用一个执行器和一个上传器，默认最多积压 8 个结果、8 MiB 原始输出；接新任务前预留最大双流输出空间。达到任一上限后停止领取新任务，但继续接收控制信息和重试上传。upload_bytes_per_second 可限制原始输出上传速率。控制端读取上传请求体、写入分块时不占用任务队列锁；最终任务 JSON 快照提交仍是共享存储瓶颈。

私有管理接口 /v1/metrics 和 tack metrics 提供连接失败分类、请求次数和耗时、进程资源、状态 JSON 写入以及结果积压。长轮询耗时包含空闲等待，不等于 RTT；任务排队、观察到的启动、取消和结果传输时延采用控制端时钟。指标不含凭据或任务输出；节点自报指标不参与鉴权。计数在进程重启后清零，Go 堆占用不是 RSS，JSON 写入字节不是物理闪存写入量。

Linux 使用独立进程组进行取消和超时回收；主动脱离进程组的守护进程不属于第一阶段的完整清理保证。Windows 的完整进程树管理使用 Job Object，创建进程、加入 Job 和恢复执行必须避免子进程先运行的竞态。平台能力或验证不足时必须在文档中注明，不将交叉编译视为运行验收。

## BusyBox 运行环境

BusyBox 作为独立组件放在部署层指定的目录，通过绝对路径调用。Node 的协议和状态读写不依赖机器先存在 shell。完整发行包携带对应架构的 BusyBox；精简包可以配置已有 BusyBox，但部署验收必须探测其 ash 和必要 applet。

Linux 构建采用经过验证的静态链接版本，启用 ash 和约定的基础 applet。Windows 评估 busybox-w32，按路径、编码、权限和命令行为差异测试。portable-sh 只承诺测试覆盖的共同子集，不承诺 Windows 与 Linux 的系统管理命令互换。

第一阶段支持配置 BusyBox 路径并执行回退；BusyBox 二进制的构建、打包、源码归档和签名在平台发行阶段完成，不从任意下载地址动态获取可执行文件。

## 平台目标

| 平台 | 目标与验证 |
| --- | --- |
| Linux amd64 / arm64 | 标准发行目标，原生或完整系统测试 |
| Windows amd64 / arm64 | 标准发行目标，单独验证进程树、脚本、路径、编码和服务生命周期 |
| CentOS 6 x86 | Legacy 构建，以 Go 1.23.12 为起点，真实 2.6.32 内核验证 |
| Linux ARMv5 / v6 / v7 | 尽力支持，保守指令集与浮点选项分别构建 |
| Linux MIPS / MIPSLE | 尽力支持，区分大小端，优先软浮点 |
| Linux MIPS64 / MIPS64LE | 按设备需求扩展，独立确认内核与 ABI |

关闭 CGO 减少系统 libc 依赖，但不能消除内核、CPU 和运行时最低要求。Go 官方将 2.6.32 内核支持终点列为 Go 1.23.12；ARM 的旧版条目最低为 3.1，不能把 CentOS 6 的 x86 结论推广到所有嵌入式设备。极简内核还需要 futex 和 epoll。

Legacy 产物仍需要独立评估旧工具链与标准库的安全维护。保留现代 SSH 修复，不等于 Go 1.23 标准库获得了全部后续安全更新；不以成功编译替代漏洞修复和兼容性验证。Modern 与 Legacy 的选择及替换由外部部署层负责，同版本切换保留完整状态与身份，不能根据连接错误自动降级。

嵌入式默认限制并发、输出和日志写入。Node 只以前台进程运行，SysV init、systemd、OpenWrt procd、厂商 NAS 启动机制和 Windows 启动方式由外部部署层负责。`state_persistence` 由部署层明确声明 durable 或 volatile，Node 不探测挂载类型或自动搬迁。volatile 存储在重启后可能丢失去重记录，控制端记录这一能力限制。

## 部署与常驻职责

部署 skill 位于 [skills/tack-deploy](../skills/tack-deploy/SKILL.md)。路径是现场部署记录，不是 Node 内置策略。Node 不修改启动项、创建用户、安装自身、重新挂载根分区、扩容 overlay 或选择持久化位置。

部署层分别确定程序目录、配置与凭据目录、任务状态目录、临时工作目录、日志去向和启动定义位置。程序与凭据可位于只读挂载；任务状态和工作目录需按运行账户可写。工作目录只承载脚本和临时数据，不要求脚本文件本身可执行；Node 与 BusyBox 的程序所在挂载必须可执行。

对 NAS 检查根分区只读性、数据卷挂载时序和厂商支持的启动钩子；对路由器检查 overlay 可用空间、闪存写入成本和固件升级保留规则；对临时根文件系统明确哪些数据跨重启保存。需要时由外部启动包装脚本在卷挂载后创建临时目录，再 exec Node。Node 只接收最终配置，路径不可用时返回错误。

部署记录包含目标、运行账户、各目录、存储保留语义、启动机制、依赖挂载、日志策略、二进制哈希及验证等级。首次先前台验证注册与无副作用命令，再配置显式命名的常驻方式。重启验收按用户允许的维护窗口执行，不把一次成功启动当作重启后可用。

## 商业授权与发布保护

商业逻辑和授权签发私钥保留在托管控制面。Node 只保存节点凭据和验签所需公钥。复制文件不能获得新的服务授权；客户控制设备时仍可分析或修改本地程序，混淆和加壳提高成本，不构成绝对防逆向保证。

发行流水线为：固定工具链 → 编译混淆 → 尝试加壳 → 验证最终二进制 → 签名与校验清单 → 发布。Garble 与 Go 版本配对固定；Legacy 构建单独验证旧版混淆工具。UPX 可作为压缩壳候选，不能代替服务端授权。

Node 默认要求尝试加壳。通过平台验证的产物加壳交付；工具不支持或运行失败时，只能按记录在发行清单中的平台例外交付混淆版。例外记录工具版本、错误、验证结果和原因。Windows 文件签名在所有二进制变换完成后执行。

保存源码提交、依赖、工具链、混淆参数、诊断资料和客户发行批次标识。验证等级分为 compile、emulated、native，不能将编译成功描述为真机支持。更新需校验来源与完整性；更新回滚及密钥轮换属于后续阶段。

部署文档和基础启动配置提前随第一阶段提供。这里的 C2 指产品提供方控制的托管服务器，不预设云厂商或已有部署环境；示例使用自定义域名与 HTTPS。客户机常驻使用明确命名、可检查、可停止和可卸载的系统服务或启动任务。第一阶段预配置节点注册，后续再替换为短期注册令牌。

第一阶段为开发基线，不作为商业生产发行。生产交付需完成身份与审计、平台验证以及默认混淆加壳等阶段。v3 通过持久化递增序号水位压缩去重记录，最终确认后再回告回执，控制端才按时间、字节和条数淘汰历史；正常历史积累不再阻止接单，未确认结果占满容量时仍保留必要背压。诊断日志默认关闭，显式选择文件时按大小轮转；输出采用头部加环形尾部，临时文件先恢复再回收。协议与升级不变量见 [保留策略](tack-retention.md)。连接、后台任务与缓冲区的资源生命周期检查和可重复长跑测试见运行说明。当前实现及运行步骤见 [management README](../management/README.md)。

当前阶段 0 的设计与部署 skill、阶段 1 的开发基线以及阶段 1.1 的链路与结果补传已落地。阶段 5 的[混淆加壳构建与产物验证](build-protection.md)已提前接入；签名、升级回滚及阶段 2–5 的其余工作尚未完成。具体通过的检查和未验证平台见 [验证记录](../management/VALIDATION.md)。
