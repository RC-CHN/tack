# 低占用与弱网优化实测（2026-10-23）

本轮优化 management Node 的故障重试和指标采集开销。目标是减少无效分配、文件读取和运行时扰动，维持背压、结果校验、取消和断点续传语义。没有把吞吐提升作为成功条件。

## 改动

1. 上传先发送已有的探测请求。服务端不可用时，不再提前读取、校验整份结果或分配 64 KiB 分块缓冲区。探测成功后仍验证文件身份及 SHA-256；即使服务端声称已经完成，也不会跳过本地校验。需要发送正文时才分配至多一个分块。
2. 指标采集改读 `runtime/metrics` 的堆对象字节数，复用受锁保护的采样槽，避免 `runtime.ReadMemStats` 的全局暂停。堆指标仍包括存活对象及尚未回收的对象，不是 RSS。
3. 已到期的限速等待直接检查取消并返回，不再创建定时器。取消优先检查修复了已取消上下文与已到期定时器同时可读时，偶尔返回成功的问题。

## 测量方法

同一 Linux amd64 主机，Intel Xeon CPU Max 9470C；两个 Node 均使用 Go 1.23.12、`-trimpath`、非 race 构建、`GOMAXPROCS=2`，未设置 GOGC/GOMEMLIMIT/GODEBUG。资源夹具使用 Go 1.27.0。未修改产品默认 CPU 配置。不能把这里的数据直接与之前不同 GOMAXPROCS 的报告比较。

微基准每项 `500ms × 5`，串行测量，表中为中位数；原始日志与 `summary.json` 保留最小值、最大值和样本数。先测 before，再测 after，没有混跑其他任务测试。不是置信区间或真实网络吞吐排名。

## 独立 Node 进程对照

使用同一个夹具，H1、H2 各进行三轮 before/after 对照，共 12 次；奇数轮 before→after，偶数轮 after→before。每次包含四个 10 秒阶段：预热后空闲、两份最大结果积压、全断网、恢复后空闲。每份结果的 stdout/stderr 各 1 MiB；第三个任务必须保持排队，恢复后验证三份完整结果及恰好执行三次。

资源采样仅包含 Node，排除子命令、Controller 和夹具；不主动触发 Node GC。所有 12 次通过原有 32 MiB RSS、FD、CPU、写盘、日志、背压、恢复和退出门限。

两边每个 10 秒空闲及恢复后空闲阶段，均观察到 **0 CPU ticks、0 流字节、0 读取/写入字节、0 诊断日志**，FD 为 8；全断网阶段 FD 为 6。CPU tick 分辨率为 0.01 秒，0 ticks 不能解释为物理耗电为零。流字节不包含 TCP/IP 开销与重传。RSS 范围重叠，不能宣称稳定的峰值 RSS 降幅；确定的收益是故障期间少分配、少读文件。

恢复耗时包含原有随机退避。本次 H2 的 after 三轮确实更慢，因此额外进行了固定种子的诊断对照，结果与限制记录在下方；不以这三个样本推导恢复速度提升或 p95/p99。

固定种子诊断使用相同二进制和夹具，仅设置 `GODEBUG=randautoseed=0`（Go 1.23.12 的默认种子固定为 1），H2 各运行一次。恢复至三份结果验证完成为 **7.907041 → 7.921736 秒**，差约 15 ms；两边断网阶段均尝试连接 4 次，所有门限通过。它支持随机退避是前三轮差异主要来源的判断，但单个固定种子不能证明所有时序下都没有退化。生产代码没有改变随机种子或退避参数。诊断完整数据独立保留在 `fixed-seed/`，不混入上面的三轮统计。

## 回归验证

- Go 1.23.12：Node、runner、protocol、rotatelog、telemetry 全部 race 测试与 vet 通过。
- Go 1.27.0：Controller、管理集成测试全部 race 与 vet 通过；共享夹具 race/short、vet 与完整迁移覆盖检查通过。
- H1/H2 的受限传输、丢失已提交分块的确认、恢复、取消和静默连接退出，另外重复三次通过。
- 隧道恢复、16 路共享连接恢复、静默 SSH 握手取消，race 下各重复三次通过。
- 独立网络命名空间：2 ms netem 延迟、2% 丢包、4096 kbit/s、seed 7；夹具另含每方向 40 ms 延迟和 64 KiB/s 限速。H1/H2 完整性、续传与取消均通过，17.10 秒，netem 记录 32 个丢弃包。宿主网络没有修改。
- Windows amd64 Node 测试二进制交叉编译通过；未在 Windows 原生运行。
- shell 语法、actionlint、`git diff --check` 通过。

新增反例验证不可用探测不提前读结果；服务端恢复后，即便声称结果已完成，损坏的本地结果也不会被发送、接受或删除。现有原子修复后重新打开文件、崩溃恢复、任意偏移续传和确认落盘后删除测试继续通过。

## 复现与证据

`before/`、`after/` 保存微基准日志和源码哈希；`process/` 保存交替进程对照的逐秒采样、日志、二进制身份和夹具源码身份；`checks/` 保存回归结果。`optimization.patch` 是本轮三个生产文件的独立差异。可在独立副本中反向应用该补丁，构建 before；工作区其他改动需要保持一致，不能只凭 HEAD 标识推断源码相同。

```sh
# 使用同一个 Go 1.23.12 构建修改前/后的 management/node。
GOMAXPROCS=2 scripts/compare-node-footprint.sh /tmp/before-node /tmp/after-node /tmp/new-comparison 10 3

# 在 management/node 中，两个版本各运行相同命令：
GOMAXPROCS=2 go test -run '^$' -bench 'Benchmark(SpoolUpload|BacklogMetrics|ReadyDelay)$' -benchmem -benchtime=500ms -count=5 .
# 在 management/protocol 中：
GOMAXPROCS=2 go test -run '^$' -bench 'Benchmark(Snapshot|OutageCounters)$' -benchmem -benchtime=500ms -count=5 ./telemetry

# 重新计算保存数据的统计：
python3 -B scripts/summarize-resource-benchmarks.py management/validation/2026-10-23-resource-optimization
```

未将二进制加入仓库，原始二进制 SHA-256/大小和构建设置保留在 manifest 及 `excluded-artifacts.json` 中。`process/RUNNER-SHA256SUMS` 保留运行器的原始清单，其中包含已省略的测试二进制；整个归档使用根目录的 `SHA256SUMS` 校验。非剥离 Node 文件从 8,945,609 B 增至 8,963,131 B（+17,522 B，约 +0.20%）。校验整个证据目录可在该目录执行 `sha256sum -c SHA256SUMS`。

这些是本机短时、限定工作负载的数据，不是长时间弱网、低功耗设备、默认全部 CPU 配额或全部输出模式下的通用占用承诺。Windows/其他架构的原生运行尚未验证。
